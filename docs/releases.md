# Автоматические выпуски

`Weekly release` работает на GitHub-hosted Ubuntu по воскресеньям в 03:17 UTC / 06:17 МСК. Есть ручной `workflow_dispatch`. Расписание запускается только из `main`; параллельные выпуски сериализованы, job ограничен 90 минутами. GitHub может задерживать scheduled runs и отключать расписание публичного репозитория после 60 дней отсутствия активности; статус расписания входит в контроль обслуживания.

## Последовательность

1. Установить зависимости и выполнить тесты Node.js и PowerShell.
2. Скачать индекс из последнего опубликованного GitHub Release; проверить неизменность исходной истории и соответствие тегу. Для исходного v2.0.0 используется `api/releases.json`.
3. Просканировать Majestic Million: до миллиона доменов рейтинга, 400 параллельных запросов, до 100000 дополнительных origins. Кэш между выпусками не используется.

   В пределах одного регистрируемого домена (включая поддомены и каждый адресат редиректа) работает один запрос, с интервалом между стартами не менее 250 мс. Слот удерживается до чтения или отмены тела ответа. На исходный домен рейтинга разрешено до 100 дополнительных origins, включая всю цепочку обнаружения: поддомены и переход к другому домену квоту не обнуляют. Перед сбором проверяется доступность непустых каталогов Bitwarden и Apple. Коды сетевых ошибок сохраняются в evidence для диагностики неполного сбора.
4. Проверить свежесть снимка, JSON Schema, статистику, содержимое фильтров и delta, исторические SHA-256. Падение охвата рейтинга более чем на 10%, общего числа связей или любого типа более чем на 30%, пустой набор и ошибки внешних каталогов блокируют выпуск. Это сигнал неполного сбора, а не автоматическое доказательство исчезновения связей.
5. Увеличить patch-номер набора, создать draft Release, загрузить файлы, скачать их обратно и сверить SHA-256. Опубликовать только после readback.
6. Вызвать reusable workflow GitHub Pages, который заново скачивает опубликованный индекс, строит и валидирует весь API, затем развёртывает его.

## Артефакты

- `rf-credential-relationships-vX.Y.Z.json`: типизированные связи.
- `rf-scan-evidence-vX.Y.Z.json`: доказательства и диагностика сбора.
- `vaultwarden-equivalent-domains-vX.Y.Z.txt`: группы для импорта.
- `SHA256SUMS.txt`: SHA-256 трёх файлов данных.
- `releases.json`: полный индекс версий и immutable locks API. Его digest также возвращает GitHub Releases API.

`api/releases.json` в Git — исходная закреплённая история. Автоматические выпуски расширяют её через release asset, не коммитят результаты сканирования и не меняют исходники. Каждый тег указывает на проверенный коммит сборщика. Версия npm-пакета обозначает код, patch-версия набора — снимок данных.

## Повторы и восстановление

Scheduled run не создаёт второй выпуск в ту же календарную неделю UTC (воскресенье–суббота). Ручной запуск намеренно допускает дополнительный выпуск. Существующий draft следующей версии скачивается и проверяется; завершённый пакет публикуется без повторного сканирования. Неполный или повреждённый draft останавливает конвейер, опубликованные файлы никогда не перезаписываются.

Завершённый сбор сохраняется в artifact `scan-results` на три дня, до подготовки релиза. При исправлении ошибки подготовки можно передать ID прежнего запуска в `scan_run_id`; проверка свежести по-прежнему допускает только снимок не старше суток. Исходный API проверяется до долгого сканирования.

Если релиз опубликован, а Pages упал, достаточно повторно запустить `Deploy static API`: он восстановит сайт из последнего опубликованного индекса. Если сработал порог качества, сначала выяснить причину в Actions и проверить доступность источников; не ослаблять порог для публикации заведомо неполного снимка.

Workflow использует только стандартный `GITHUB_TOKEN`. Он передаётся явно шагам чтения состояния и публикации, отсутствует в окружении сборщика; checkout не сохраняет Git credentials. Права `contents: write` нужны для релиза, `pages: write` и OIDC — только для развёртывания Pages. PAT, внешний сервер и платный планировщик не нужны.
